# J614s GPU context observation trial

This experiment investigates Linux PR #804 on the 16-core T6040. Its trial kernel is based on the installed source pin `24bfd5ba2c182bf67d40c7d02f4947d124f04fa4`, and `instrumentation.patch` adds PID-gated summaries of the compute preemption and operand-state buffers at queue-idle boundaries. It never intentionally prints their contents or GPU addresses. The trial retains the normal timer and scheduling policy. The instrumented release ends in `-gpuobs`, not `-ARCH`, so Aurora's boot updater will not select its DTBs as the latest packaged kernel.

`gpu-live-marker.c` and `live-marker.comp` exercise the physical GPU using low-versus-medium and same-priority compute queues, CPU-checked output and an in-dispatch marker. Host observation of that marker is a platform-specific diagnostic, not a Vulkan guarantee of host/device visibility before a fence. Tracepoints record command publication and firmware completion intervals. `analyze-trial.py` reports paired before/after buffer fingerprints and candidate interval nesting; neither changes nor interval nesting alone prove a context save or restore. Lack of an observed event is inconclusive, not proof that preemption never happens. The tests do not qualify render deflake or establish every offset.

The trial source archive and verified local source delta, kernel configurations, compressed symbol-bearing kernel, compiled workload, SPIR-V and private results are archived at `/home/michal/.local/share/m4rch-archive/cleanup-20261102/cache/gpu-context-trial/`. The duplicate extracted source, build tree and staged module copy were removed after comparison; see the archive README for reconstruction details. The installed trial modules and boot image remain in place, but their `build` symlink points to the former build directory and cannot be used to build external modules. Set `M4_GPU_TRIAL_DIR` to a prepared private trial directory containing the binary and SPIR-V before reusing the runner; it defaults to the ignored `cache/gpu-context-trial/`. The exact build and release must be verified before staging. After booting the prepared one-shot trial, `run-trial.sh` refuses any other kernel, enables a per-PID observer only while the bounded workload runs, captures its trace and hashed summaries privately, and clears the PID and trace instance on exit. Restore the normal GRUB entry on the next boot; the normal kernel, initramfs and bootloader are not replaced by this experiment.

A bounded baseline on the normal kernel observed the marker and CPU-checked outputs. The trace included one same-priority round whose contender interval lay inside the background interval; other rounds completed too early or outside that interval. This confirms the instrumentation route is worth trying, not that either dispatch was preempted: two GPU intervals can overlap through concurrency.

## One-shot trial staged on 2 November 2026 (historical)

At staging, GRUB `next_entry` selected `m4gpu-context-trial` once; that one-shot selection was consumed. The trial uses `/boot/vmlinuz-linux-gpuobs`, `/boot/initramfs-linux-gpuobs.img` and `/usr/lib/modules/7.3.0-1-14-gpuobs`; its initramfs has the same 177 module paths as the normal one. The normal kernel, initramfs, generated GRUB configuration and EFI stage-two bundle were verified unchanged. Their recorded hashes and the prior GRUB environment are in `/var/lib/m4rch/gpu-context-trial-20261102/`. GRUB normally clears the one-shot selection before booting and returns to its standard entry on the following boot; the normal entry is also available in the menu.

The observer is off until `run-trial.sh` targets its own workload PID. For any future trial, first verify the boot configuration and prepare a private trial directory; the runner writes its results there. A kernel fault or hang during this experimental work may require rebooting into the normal entry. Do not infer a context save from queue overlap or changed summaries.


## Instrumented boot result — 2 November 2026

Boot `40560ec0-fb1c-4fda-8f64-7364d776a911` ran the one-shot `7.3.0-1-14-gpuobs` kernel. The owner reported a successful boot. The PID-gated observer recorded 336 comparable six-region before/after summaries for the bounded compute workload; 61 region pairs changed. Both operand banks, the inter-bank area, preemption buffer and other regions also changed during solo calibration, before any competing queue was submitted. These writes therefore do not identify an interrupted dispatch or establish save/restore.

The workload completed and its CPU comparisons passed (full contender output; sampled background output). All ten contenders had marker/fence observations; the analyzer found no candidate contender interval nested inside its background interval using the recorded firmware completion timestamps. Fence overlap was observed in both the low-versus-medium and same-priority cases, but cannot establish preemption. The host's live shader marker and the firmware completion start timestamp also do not provide an independently calibrated common start signal. Treat the result as inconclusive, not a negative proof or a validation of the buffer offsets. No matching GPU or DART fault appeared in the checked kernel log.

The observer parameter was reset to zero and its temporary trace instance removed after the run. The original results are in the `result.aSzWFn/` subdirectory of the private trial archive above. The one-shot GRUB selection cleared, so the normal Aurora kernel remains the next-boot default; the trial modules and boot artifacts were retained for the investigation. A later boot is running the normal kernel.

## Independent reference and context-switch leads

The local EFI stub contains `kernelcache.release.mac16j` for macOS 26.6.2, build 25G83, the firmware build used by this trial. Its Apple AGXG16X host driver has symbols for enabling, resetting and reading per-data-master context-switch latency histograms, and strings naming histogram buckets. Static inspection shows a corresponding control operation and code that reads histogram-sized data. This is a promising independent lead, not a verified Linux firmware interface: the complete request, synchronization, storage and meaning of the counters still need to be established. The driver is a generic native binary, not a recording of the branch and layout actually used by this 16-core GPU. Extracted Apple binaries are in the private archive under `cache/gpu-context-trial/macos-reference/`; keep them private and do not publish them or firmware memory dumps.

Aurora's current G17 device-control enum does not implement the observed native operation. Do not issue an inferred firmware command until the complete ABI and a recovery plan are understood. If the histogram can be accessed, compare idle, solo and competing workloads and correlate a counter increase with a completed, correctness-checked dispatch. A histogram alone would establish only what its verified semantics imply; it would not independently validate the operand-buffer offsets or render deflake layout.

The native driver is a possible source of the allocation and register formulas, but these have not yet been traced to a 16-core-specific runtime configuration. An independent reference would require resolving those formulas and their actual inputs on this machine, or obtaining a trustworthy capture from a separate working 16-core implementation. Mesa's macOS IOKit wrapper captures user command streams, but has not been shown to capture kernel-created firmware queue state. The m1n1 hypervisor and AGX tracer are another research path, but the documented supported macOS targets do not yet include M4 and its tracer's firmware decoding needs verification for this generation. Neither route is currently a ready-made 16-core reference.
