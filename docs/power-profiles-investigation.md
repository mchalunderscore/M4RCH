# Power profiles on J614s

## 2026-10-27: Omarchy / upstream cpufreq boost driver

Omarchy's [cpufreq boost driver](https://github.com/omacom/omarchy-pkgs/blob/master/pkgbuilds/omarchy-power-profiles-daemon/cpufreq-boost-driver.patch), merged upstream after power-profiles-daemon 0.30 according to its [package recipe](https://github.com/omacom/omarchy-pkgs/blob/master/pkgbuilds/omarchy-power-profiles-daemon/PKGBUILD), uses the global boost switch for apple-cpufreq: off for power-saver, on for balanced and performance. The patch reports testing on M1 Max, not this M4 Pro.

At the initial check, the running system had power-profiles-daemon 0.30-1, active with the placeholder platform driver, and all three CPU policies use apple-cpufreq. The global boost file exists, but writes of both 0 and 1 failed with `Invalid argument`. The live `scaling_boost_frequencies` files are empty for policies 0, 1, and 8, and the live device tree contains no `turbo-mode` nodes. The running kernel source's T6040 CPU OPP tables likewise have no turbo-marked entries. Thus the boost-based driver is not usable on this configuration: its write-only probe would find the file, but profile activation would fail. The original reported boost value of 0 was restored. A failed write can flip the reported global flag due to the kernel's error path even though there are no boost-capable policies, so checking the final value matters.

At that stage no package had been replaced; the original package remains cached at `/var/cache/pacman/pkg/power-profiles-daemon-0.30-1-aarch64.pkg.tar.xz`. The daemon remained active and balanced with the placeholder driver after the test.

## Frequency-cap feasibility

Omarchy has a separate proposed [frequency-cap patch](https://github.com/omacom/omarchy-pkgs/blob/master/pkgbuilds/omarchy-power-profiles-daemon/cpufreq-caps.patch) for Snapdragon X, not Apple CPUs. A short, reversible feasibility test capped policy0 only and ran `taskset -c 0 openssl speed -seconds 3 -bytes 8192 sha256`. At the original 4.512 GHz ceiling, throughput was 3,368,575 kB/s; at a 3.300 GHz ceiling it was 2,470,167 kB/s; after restoring 4.512 GHz it was 3,307,502 kB/s. The original ceiling was restored by an EXIT trap. This establishes that a cap changes performance in this workload, not that it saves energy or that the Snapdragon percentages are suitable for T6040. Balanced and performance would need carefully defined semantics, and battery energy, thermal behavior, responsiveness, conflict handling, and suspend/resume would need validation before persistent integration.

## J614s cap driver trial

The [J614s adaptation](../packages/power-profiles-daemon-m4rch/j614s-caps.patch) builds on Omarchy's unmodified boost and cap patches and is restricted to the live device-tree compatible strings `apple,j614s` and `apple,t6040`. On this machine it leaves balanced and performance uncapped, preserving the existing default. Power-saver uses a provisional 75% of each cluster's maximum, rounded to the nearest available frequency: 3.300 GHz on both P clusters and 1.788 GHz on the E cluster. The 75% choice is experimental, not an M4 Pro optimum. Other Apple machines retain the upstream boost method. Sources are power-profiles-daemon 0.30 tag commit `5b4994c8a91290481bef87a5bae95391d0ec677f` and the vendored Omarchy patches. The additional NVIDIA patch is a prerequisite for applying Omarchy's patch series to 0.30; it is not used by this machine.

The built daemon successfully advertised its `cpufreq` driver via D-Bus, switched all three live CPU policy ceilings, and exposed balanced, performance and power-saver. Targeted integration tests passed for J614s selection and profile changes, upstream Apple boost, Snapdragon caps, nearest-frequency selection, new policies, exit cleanup, and simulated resume. The resume check was a mock integration test, not a live sleep test. Omarchy's cap implementation restores hardware maxima on exit rather than preserving a preexisting third-party cap, and can report partial success if some policies fail; those conflicts and error semantics need attention before a durable deployment.

The live battery trial used four 20-second runs of `openssl speed -multi 8 -seconds 20 -bytes 8192 sha256` in balanced, saver, saver, balanced order. It sampled battery `power_now` every second, averaging samples after the first four seconds, and measured timer wake delays while the workload ran. The trial source and complete samples are preserved in `out/retired-experiment-sources-20261028.tar.gz`.

| Metric | Balanced, two-run mean | Power-saver, two-run mean |
| --- | ---: | ---: |
| Total battery discharge under workload | 39.17 W | 29.94 W |
| SHA-256 throughput | 23.57 GB/s | 19.84 GB/s |
| Battery energy per unit of completed work, estimated | baseline | about 9% lower |
| Timer wake delay, 99th percentile | 0.29–0.43 ms | 0.44–0.47 ms |

The power comparison is about 24% lower draw and 16% less throughput, for this short CPU-heavy workload. The energy-per-work estimate uses average power divided by throughput; power samples omit the first four seconds while throughput covers the full 20 seconds. Battery power may lag and background draw varied: balanced runs averaged 37.18 and 41.17 W, versus 29.22 and 30.65 W for saver. These are not estimates of whole-day battery life, idle savings, or other workloads. Timer delay is a scheduler proxy and does not measure KDE frame latency. During a separate attended power-saver desktop trial, the owner reported that scrolling, moving windows, and trying an app felt normal.

## Hardening and promotion

On 2026-10-27 upstream [MR !239](https://gitlab.freedesktop.org/upower/power-profiles-daemon/-/merge_requests/239) remained open; [MR !237](https://gitlab.freedesktop.org/upower/power-profiles-daemon/-/merge_requests/237) was merged. The J614s-specific [safety patch](../packages/power-profiles-daemon-m4rch/j614s-cap-safety.patch) preserves limits already present when the daemon starts, adopts external changes observed between switches, restores only limits it still owns, and treats a multi-policy change as a transaction with rollback on failure. CPU sysfs does not offer compare-and-swap: another writer racing between a read and a write cannot be completely excluded. Abruptly killing the daemon can also leave a cap behind; avoid running multiple independent frequency managers. Other boards retain upstream behavior.

On real hardware, sysfs accepted a limit write before the updated value was readable. The first hardened staging attempt consequently reported failure, and a P-cluster limit was manually restored to its recorded original. The driver now waits up to two seconds for the requested limit to become visible before deciding the write failed; the corrected package switched all three policies successfully. Five package integration tests passed, covering profile switching, preservation and external changes, restoring owned limits, rolling back an actual partial write, and simulated resume.

The corrected packaged daemon was staged with power-saver selected and a timed stock-service rollback. The user closed the lid and reported normal wake; systemd logs show suspend from 22:45:58 to 22:47:33. After resume the daemon remained active, the profile was `power-saver`, and policies 0, 1 and 8 remained at 3300000, 1788000 and 3300000 kHz. The temporary trial was cleaned up and the previous ceilings restored.

The tested `power-profiles-daemon-m4rch` 0.30-1 package is now installed and its service enabled. Installed power-saver, balanced, and performance switching was verified; balanced and performance both restore the pre-existing uncapped ceilings. Balanced was left selected. The original package is cached at `/var/cache/pacman/pkg/power-profiles-daemon-0.30-1-aarch64.pkg.tar.xz`. To revert, install it with `sudo pacman -U /var/cache/pacman/pkg/power-profiles-daemon-0.30-1-aarch64.pkg.tar.xz`, accept removal of the m4rch package, and restart `power-profiles-daemon.service`.
