# Retained-cycle crashlog diagnosis, boot df540

The post-event reserved firmware buffer contains a complete bounded CLHE crashlog reporting **“Invalid AP power: 33”**. The matched firmware handler identifies this as a duplicate AP power-state assertion: wire state `0x20` is recognized and converted to internal state `33`; requesting the already stored state reaches the captured panic callsite. This is evidence of a firmware crash, not a harmless initial crashlog-buffer offer.

The guarded read-only DATA capture is `out/gfx-native-running-cycle/post-event-fw-data-df540/data-after.bin` (1,277,952 bytes, SHA `7204e27e9cc9fd5f5a145378b050a062f5f33dc20ed651e7d3d2090ba30caded`). Its capture metadata SHA is `f802354348632c34e8f7bf422d0edb860059142c5018177cd56775c7b826da6d`. The sampler loaded once and underwent its normal release; the GPU owner's note, reference count and host state stayed unchanged, with all 174 backing allocations retained and no GPU control commands. Root performed that separate capture; this diagnosis used saved files only.

The crashlog starts at DATA offset `0xa0000`, firmware address `0x10001de4000`. Its declared size `0x910` (2,320 bytes) fits both the new EP1 4 KiB descriptor and the original cold 32 KiB extent. It has ten ordinary sections and an exact repeated 32-byte opening header as its footer at `0x8f0`; task 6's stack has fourteen addresses. The string is Cstr ID 1. No register section is present. The six decoded asynchronous-error fields are zero. Unknown record bodies remain uninterpreted.

The footer requires the bounded decoder's explicit repeated-header adaptation. The maintained Linux decoder tests offset+12 as section length before switching on CLHE; here that field is flags `0x820`, larger than the remaining `0x20` bytes. We therefore do not claim that the unchanged Linux parser completely validates this buffer. The adapted parser validates the exact repeated header, all declared record bounds and the final total. No earlier expected-root-rejection success assertion is inherited.

The actual Cver text is `RTKit: RTKit-3255.160.4.release - Client: not set`. This version-303 record places the text at payload offset24, after a16-byte GUID and8 zero bytes. The reused Linux offset16 lens yields an empty string; the actual offset24 bytes are preserved separately without inferring the unknown fields. The bounded Ccdp mapping record also reports firmware DATA VA `0xfffffc0000060000` to physical `0x10001d44000`, supporting the DATA address translation used below.

The firmware TEXT from this boot has SHA `b474bc31543db4e60e119da0efc20127a6918e22ff78e77ebce4de56aebcd8c7`. Its instructions exactly match the established image after zeroing only two qualified tagged eight-byte metadata payloads; normalized SHA `190cef1946a23dfbde180592629631c3b28d0509a17eb76108b7c9a52accd9ac`. Bounded complete handler, conversion, lookup and jump-table ranges are pinned in the companion JSON.

At `0xfffffc00000481fc`, the handler extracts management type bits 52–55. Jump-table index B selects `0xfffffc00000482b8`. The helper at `0xfffffc0000048648` recognizes low byte `0x20` and returns internal `0x21`, decimal 33. At `0xfffffc00000482d4..482dc`, the handler compares that requested value with the stored AP state and branches on equality. The panic tail forms TEXT string `Invalid AP power: %d\n` at `0xfffffc000005cded`, stores the requested value and calls the panic routine at `0xfffffc0000048368`, which appears in the captured stack. Thus the diagnostic does not mean that wire `0x20` is unsupported.

The saved DATA lookup table points to a bounded 72-byte record at `0xfffffc00001862f0`; its ID is 0, its stored state is 33 and its endpoint pointer is `0xfffffc0000186370`. This observation is consistent with the equality assertion; it is one non-atomic post-event snapshot.

The crashlog mailbox history has 35 bounded records. It preserves cold HELLO/maps/EP1 offer/HOST B20/root/application traffic, first shutdown `0x202` and ACK `0x201`, then the second HELLO/maps/Running sequence. Its final word is the second owned HOST B20, `0x00b0000000000020`. The final combined raw stamp is `0x1de74f5e1`; Ctim is `0x1de74f7a5`, a difference of 452 raw ticks. Linux labels only the low 32 bits as timestamp and leaves the upper 32 unknown; the combined word is preserved without asserting timer frequency or host clock alignment. This chronology and the matched stack strongly identify the duplicate B20 as the trigger, but the snapshot is not a complete CPU trace.

The saved native RTBuddy analysis already shows that signalApPower(ON) skips its HOST exchange when the management endpoint's cached remote power is already `0x20`, subject to runtime flags and the selected callback path. Our bounded experiment did not bind that retained remote-state mirror and sent B20 unconditionally after Running. Cold B20 success therefore did not authorize the same transition after retained reentry. This is the concrete missing condition to investigate offline; safe live omission or continuation is not yet qualified.

The current owner remains sealed. It accepted no HOST B20 reply and attempted no second `0x202`, ACK, CPU stop, physical OFF or PM put. The second reference and all 174 backing identities remain retained. Do not echo EP1 or resend B20. The preboot buffer was zero, but the preboot/post-event difference alone does not establish exact write time. DATA sampling was non-atomic and firmware cache freshness remains unknown. No application rejoin, DMA retirement, work submission or rendering success is established.

The first offline decoding pass failed only its final output write inside the root-owned capture directory; its saved-file-only replay wrote `out/gfx-native-running-cycle/offline-crashlog-decode-df540.json`. Frozen owner sources, modules and previous qualifications were unchanged.
