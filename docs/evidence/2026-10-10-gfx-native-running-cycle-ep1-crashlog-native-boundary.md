# EP1 event after HOST ON: crashlog boundary

Actual bootdf540 completed a second START, HELLO12, both map ACKs and exact boot7/20, then wrote its single owned HOSTB20. Its fifth removed frame at312.361662 was EP1 word0x0010110001de4000/meta0x0010450000000001, refused withEPROTO before any accepted B20 reply or second202. No second ACK, CPU stop, OFF or PMput occurred; the second reference remains retained. Timing does not correlate the frame to HOSTB20 or prove another reply is pending.

The cold sequence on this boot had EP1 START, word0x0010810001de4000 and a qualified reserved descriptor echo before7/20 and B20reply. Both words decode to address0x10001de4000 and4KiB units, but the cold word reports32KiB while this event reports4KiB. Both are aligned and mathematically within the frozen reservedFW DATAextent. Bounds alone do not distinguish buffer negotiation from crash notification.

The complete native RTBuddyCrashlogEndpoint message handler distinguishes those meanings using its own local+a8 buffer object. When that object exists, it marks state124=2 and calls_handleCrashlog(false), which calls RTBuddy::onPanic, obtains/decodes buffer contents and enters crash reporting. It does not echo the descriptor on that branch. Only the no-buffer branch with mode54..55=0 and a nonzero44-bit address obtains existing IOP memory and constructs a descriptor reply; zero address and other modes take different allocation/mapping paths. Native reply construction reencodes address and rounded size from its memory object rather than blindly echoing an arbitrary word.

The native power callback preserves+a8 for memory-preserving state2; the common predicate returns true for state<3. Native initialization begins with+a8null. Neither the actual native runtime object nor its+a8 value exists in our Linux trial and neither is inferred from the firmware address. The clean local maintained Linux RTKit source independently treats EP1 type1 as negotiation only whencrashlog_buffer.size is zero; with an existing buffer it marks the coprocessor crashed, snapshots and decodes that buffer. Its Rust wrapper maps a nonzero suppliedIOVA separately from allocating a zeroIOVA request.

Crash decoding requires actual bytes. Native and Linux parsers recognize CLHE magic0x434c4845 with a32-byte header, declared size and bounded sections; native also recognizes CLGH multi-crash containers. The only saved reservedFW DATAcapture is data-before.bin, made before cold startup: targetoffset0xa0000 begins with a zero4KiB page. Current objects/owned snapshots copy allocated host graph pages and do not capture the reservedFW buffer. NoCLHE/CLGH signatures appear in those saved host snapshots, which cannot rule out a crash elsewhere. A current reserved buffer dump cannot be recovered from the available captures.

The EP1 event therefore remains unresolved. Retained-buffer native/Linux semantics make a crash notification a concrete possibility. A harmless required service echo, pending HOST reply, successful HOST state, second shutdown, application rejoin and DMA retirement are unproved. No next echo kit is proposed. The useful diagnostic boundary is a separately authorized qualified postevent reservedFW buffer capture followed by offline header/section validation. This review saved bounded native function/source hashes and exact capture observations only; it made no source changes, new build, tests, module load, hardware read or control request.
