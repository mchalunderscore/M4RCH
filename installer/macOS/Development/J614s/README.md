# M4RCH J614s integration

This directory carries the M4RCH integration for the vendored Aurora installer. The target is the M4 Pro Mac16,8, `apple,j614s`, T6040. Aurora's experimental admission is adapted from installer PR 49 and requires the owner's explicit Full send choice; public builds continue to reject unsupported boards.

On 31 October 2026 the owner installed Aurora ALARM Minimal using the local developer installer, enrolled its stage 1 and booted the resulting J614s system. The booted kernel is `7.3.0-m4rch-aurora1`; the stage-2 payload hash is `6a824dd6177a3b895331fa5e32431b7612e7038a5bbc470bfc498956cf7f0d9b`. That boot does not establish production support or all hardware functionality.

The normal `packages/linux-m4rch` recipe now describes the booted kernel and Aurora initramfs integration. `packages/tools/native.py` consumes verified retained inputs from `cache/aurora1-promotion/linux-package`, which must be supplied locally and are never committed. Its pinned m1n1, J614s DTB and U-Boot inputs reproduce the stage 2 above. Run `python3 installer/macOS/Development/J614s/preflight.py .` and `python3 installer/macOS/Development/J614s/build_stage2.py . /path/to/new-output` from the repository root. These verify and assemble retained inputs; they do not enroll stage 1 or change disks.

The rebuilt kernel source is Aurora Linux `23827fe87f4ffbabf5b7907a5907f9316286ce55`, with the ordered promoted M4RCH patches. `build-kernel-in-guest.sh` records the build invocation; kernel sources, toolchain and local artifacts must be supplied separately. `prepare_rebuilt_package.py` stages the standard M4RCH package recipe, rather than maintaining an installer-only recipe. A separate image-building workflow must supply authenticated Aurora images and a privately retained stage-1 template; neither is in this repository.

`build_image_payload.py` and `repair_payload_zip.py` rebuild private images and strip inherited ZIP64 fields before the ZIP writer creates new ones. The uncorrected archive was rejected by Aurora's real validator. The signed catalog must be regenerated with a higher sequence whenever the image changes. Developer signing keys, generated catalogs, Apple firmware, device calibration and final images must remain private and are not repository content.

The first Linux boot lacked BCM4388 C2 Wi-Fi firmware. The installer selected a Recovery image without the required Mriya files and upstream's converter excludes that firmware directory because an old IPSW contained broken data. The owner confirmed Wi-Fi works after provisioning firmware from this Mac's current macOS installation. On macOS, `python3 installer/macOS/Development/J614s/prepare_wifi_firmware.py /path/to/new-private-directory` prepares the local bundle; transfer it privately and use `install-wifi.sh` in Linux. This is a documented recovery path, not yet an automatic installer fix. Do not publish its output.

Aurora's generic `update-m1n1` is disabled in the installed candidate because it cannot yet be trusted to reproduce the J614s split loader and new ESP layout. Restoring automatic bootloader updates requires a package-managed updater and native verification; do not replace a working enrolled loader with the generic output. The stock Aurora SEP loader is masked because it enables xART writes and keybag provisioning; fingerprint functionality has not been requalified in this fresh installation. The initial installation used unencrypted Btrfs. A conversion journal interruption edge case remains unresolved; encryption has not been qualified.
